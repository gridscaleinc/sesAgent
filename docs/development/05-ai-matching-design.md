# Secure Talent Match AI Matching Design V0.1

## 1. 目标

匹配模型 V0.1 以透明、可解释、可调为优先目标。系统应结合规则权重、语义匹配和 LLM 解释生成，输出可供 HR 人工确认的候选人排序，而不是自动录用或自动淘汰结论。

## 2. 默认评分维度

| 维度 | 默认权重 | 说明 |
| --- | --- | --- |
| 技能匹配 | 30% | 核心技术栈、工具、框架、证书等是否满足要求 |
| 项目经验 | 25% | 是否做过相似系统、相似规模、相似职责 |
| 行业 / 领域经验 | 15% | 是否具备支付、金融、制造、SaaS 等领域背景 |
| 年限与级别 | 10% | 工作年限、项目角色、技术深度是否匹配 |
| 语言能力 | 10% | 日语 / 英语能力是否满足客户沟通要求 |
| 可用性 | 10% | 到岗时间、地点、远程条件、雇佣形态是否匹配 |

项目需求页允许 HR 调整权重。匹配结果必须保存实际使用的权重，便于审计和复现。

## 3. 评分流程

1. 解析项目需求，得到硬性条件、加分条件、风险项和面试验证点。
2. 解析候选人简历，得到技能、项目经历、行业、年限、语言能力和可用性。
3. 对每个评分维度执行规则匹配和语义匹配。
4. 为每个维度收集支持证据、缺口和不确定信息。
5. 按权重计算总分。
6. 使用 LLM 生成推荐理由、风险点和人工确认建议。
7. 保存模型版本、提示词版本、权重和证据引用。

## 4. 推荐级别

| 推荐级别 | 建议分数区间 | 展示文案 |
| --- | --- | --- |
| strong_fit | 80-100 | 建议优先确认 |
| possible_fit | 65-79 | 建议面试确认 |
| needs_review | 50-64 | 建议人工复核 |
| weak_fit | 0-49 | 暂不优先，但可人工查看 |

推荐级别只用于辅助排序。页面不得将其表达为录用、淘汰、合格或不合格。

## 5. 证据与解释要求

每个匹配结果必须包含：

- 总分和分项分。
- 每个分项的简短解释。
- 支持判断的简历证据片段。
- 条件缺口或未确认信息。
- 风险点。
- 建议人工确认问题。

证据片段应尽量引用原始简历中的具体经历、技能或项目描述。若缺少证据，解释必须明确标注“未在简历中确认”。

## 6. 风险点类型

| 风险类型 | 示例 |
| --- | --- |
| 技能深度不明 | 写有 Java，但没有明确项目职责或复杂度 |
| 项目相似度不足 | 有后端经验，但未体现支付、金融或高并发经验 |
| 语言能力待确认 | 简历写有日语能力，但没有客户沟通证据 |
| 可用性待确认 | 到岗时间、地点或远程条件未写明 |
| 年限与级别不一致 | 总年限足够，但核心技术年限不足 |

每个风险点至少生成一个面试追问或人工确认建议。

## 7. LLM 使用边界

本地 LLM 优先用于解析、摘要、初步匹配和解释生成。外部 API 只能作为可选增强，并必须经过脱敏层。

LLM 不得：

- 输出自动录用或自动淘汰结论。
- 编造简历中不存在的经历、技能或证书。
- 在没有证据时给出确定性判断。
- 将受保护属性作为评分依据。

LLM 必须：

- 标注判断依据。
- 区分事实、推断和待确认事项。
- 使用“建议确认”“建议面试”“建议人工复核”等辅助判断表达。

## 8. 提示词版本管理

每次匹配结果应记录：

- 模型名称和版本。
- 提示词版本。
- 评分权重版本。
- 生成时间。
- 操作者或触发任务 ID。

当提示词或权重发生变化时，历史匹配结果不自动覆盖，需要重新运行匹配任务。
