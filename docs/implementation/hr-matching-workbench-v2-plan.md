## 1. 实施策略

优先改变页面组织，复用现有业务处理和加密数据。先让案件 / 人员列表与双向匹配形成完整工作流，再增加针对性介绍与轻量跟进。每个阶段交付可运行的闭环，不一次替换所有旧页面。

现有人员导入可用性、自社规则、Main 校验、云端脱敏与邮件手工发送边界属于回归约束。传统资料管理、导入、面试、提案能力继续可达。旧 Agent 主界面在迁移期间保留开发回退路径；不为 HR 增加必须选择的新旧模式设置。

## 4. 状态与数据契约

### 4.1 导航状态

至少分别表达：

- 业务页：案件 / 人员 / 跟进。
- 来源列表快照：查询、业务筛选、时间范围、页码、选中对象、滚动位置。
- 匹配来源：方向、对象 ID、资料版本。
- 结果选择：目标 ID，与来源 ID 独立。
- 当前详情：来源或结果目标。
- 返回栈：从匹配、管理、介绍返回到何处。
- 抽屉：Agent、导入或介绍，及其关联对象。

恢复路由不得触发有副作用动作。用户动作与页面挂载分离，避免切页、热更新或重启自动重复匹配。

### 4.2 当前对象投影

在数据访问层形成以 `{ kind, objectId }` 为键的当前视图：名称、当前版本、关键字段、业务可用性、最近业务变化时间、已读版本、稍后处理、来源及历史引用。

要求：

1. 聚合已有同 ID 动态，不覆写或丢弃历史。
2. 人员、案件采用不同的 ID 类型；禁止混用来源消息 ID、review ID、实体 ID。
3. 阅读和复制不改动业务排序时间。
4. 新版本可标未读；仅状态投影刷新不虚构新事件。
5. 稍后处理迁移按对象关联；历史多个事件标记的合并策略须通过夹具测试，不丢失已存在的稍后处理。
6. 第一轮不建立跨来源“统一人员身份”或基于姓名的自动合并表。

### 4.3 匹配任务状态

建议状态：`idle → local-running → cloud-running → completed / partial / failed / cancelled`。资料版本改变另标 `stale`，与请求是否完成分别表达。

任务身份至少包含方向、来源 ID、来源版本、匹配配置版本；受评估目标的版本集合记录在结果内。该身份由 Main 维护并用来合并重复请求。Renderer 使用共同状态禁用所有关联入口。

- 本地阶段结果可以先交给页面展示；若现有接口只返回最终结果，阶段 B 必须补充受信任的进度事件或查询契约，不能用定时器假进度。
- 首轮沿用当前有限批量评估策略；已有两个 Main matcher 的默认超时为 45 秒，具体批量上限从实现读取，集中定义后仍须验证行为。
- 重试只由明确点击触发；自动重试必须有既有受控策略，不能在组件 effect 中循环发送。
- 返回结果需验证来源与目标版本。自社、业务可用性等条件变化后清除旧结论的可用性。
- 取消通过任务 ID 传播到 Main 及网络中止能力；若第三方请求无法即时中止，应停止消费结果并准确显示已停止处理。
- 先保留会话内缓存。跨重启缓存是否新增，由真实需求决定；不得为了恢复页面自动执行一次云端匹配。

### 4.4 介绍草稿

草稿键至少包含：用途、案件 ID / 版本（可空）、人员 ID / 版本（可空）、模板 ID / 版本、语言、标准 / 省略版本。用途区分通用人员、通用案件、针对性介绍。

先通过适配现有模板、匹配证据和草稿能力交付。必须保留 HR 已编辑文本，区分系统初始生成内容和人工修改。版本变动提示刷新依据，但不静默删除编辑内容。

复制与邮件交接仍由 Main 检查资料版本和脱敏边界。只有完成系统剪贴板写入才记录复制成功；打开默认邮件客户端不创建“已发送”事件。

### 4.5 跟进与数据库演进

先评估现有 `ProposalFollowUpState`、事件与面试关联是否足够。若现有跟进只能依附于正式提案草稿，不应为了记一句备注强迫 HR 创建正式提案；可以增加轻量关系适配，具体表结构在阶段 D 开始时明确。

所有确需新增的表或字段必须给出：默认值、旧数据映射、加密存储位置、删除级联、备份修订与重启恢复验证。迁移只追加并由现有 migration 注册，不修改历史 migration。UI 位置偏好与敏感正文分开存储。

## 5. 分阶段开发任务

阶段按依赖推进，不预设缺乏依据的工期。除阶段 0 外，每阶段均要求展示真实运行页面。

### 阶段 0：基线夹具与路由设计

- [x] 固定基线提交和现有测试证据，记录两条核心路径。
- [x] 用虚构案件 / 人员准备场景：重复动态、同名不同档案、长正文、自社三态、匹配失败与迟到回复。
- [x] 定义导航快照、详情选择和匹配任务身份。
- [x] 核对现有 schema、已读和稍后处理投影，列出复用与确需迁移的部分。

完成标准：评审对象是可执行的数据契约与页面状态转移；没有遗漏的返回路径，不改真实 HR 数据。

### 阶段 A：业务主界面与对象列表

- [x] 新壳与案件 / 人员导航；默认进入业务列表。
- [x] 聊天与任务历史迁入 Agent 抽屉，旧管理和面试入口可达。
- [x] 当前对象聚合、关键字段卡片、四个直接展示的业务按钮（匹配使用主按钮样式）。
- [x] 保留时间下拉筛选与每页 20 条分页；分别恢复案件 / 人员页码与滚动位置。
- [x] 接入右侧资料，自社自动保存和完整案件正文继续可用。
- [x] 实现搜索、筛选、选中、滚动与宽度恢复。
- [x] 将导入 / 粘贴入口接到既有批次流程；返回后批次草稿不丢失。

完成标准：HR 可从两个业务列表浏览、导入、阅读、编辑并返回；同 ID 多事件只显示一张卡，同名不同档案仍独立。此阶段匹配可暂接现有流程，不宣布统一匹配体验已经完成。

### 阶段 B：双向匹配进入主区域

依赖：阶段 A 的导航状态和当前对象投影。

- [x] 统一来源摘要、进度、结果卡和右侧详情选择。
- [x] 接入两个现有 matcher，不重新实现召回算法。
- [x] 支持真实本地 / 云端阶段、部分结果、重试与取消状态。
- [ ] 统一请求锁与任务 ID，所有入口防重。
- [x] 展示适合依据、待确认、冲突；覆盖范围逐条标记。
- [x] 实现双方资料版本变化失效与明确提示。
- [x] 自社限定排除统计使用本地规则真实计算，不通过 AI 猜测数量。
- [x] 实现来源列表—匹配—结果详情的完整返回恢复。

完成标准：两个方向各完成一次有结果、无结果、失败重试和切换对象验收；查看资料与返回不新增云端调用。

### 阶段 C：上下文介绍

依赖：阶段 B 的来源 / 目标身份与有效证据。

- [x] 通用人员、通用案件、针对性介绍共用编辑界面。
- [x] 从匹配结果进入时自动关联双方，不再次选择对象。
- [x] 模板组合使用已经验证的依据，保留缺失信息。
- [x] 多模板 / 语言草稿不互相覆盖，HR 输入优先保留。
- [x] 资料变化提醒、复制版本校验、邮件交接与现有能力一致。

完成标准：从案件找人和人员找案件都能准备同一组合的介绍；不编造经历，复制 / 邮件操作不记为已联系或已发送。

### 阶段 D：轻量跟进

依赖：阶段 C 的介绍上下文及现有提案 / 面试关系梳理。

- [x] 复用既有事件或增加最小关系适配，写清最终数据结构。
- [x] 支持 HR 明确记录联系、回复、备注与下一步。
- [x] 跟进列表可回到对应案件、人员与面试。
- [x] 自动动作记录与人工业务事实清楚区分。
- [x] 完成后再开放“跟进”导航。

完成标准：不要求每条导入记录进入漏斗，不增加推广准入；记录、重启读取、编辑及回到业务上下文闭环通过。

### 阶段 E：整体一致性与默认切换

- [ ] 实机验收窗口宽度、键盘、焦点、中文 / 日文与长文本。
- [ ] 清理重复导航、无用按钮、旧界面入口文案与临时兼容层。
- [ ] 使用真实耗时记录区分本地阶段、云端阶段与界面交互等待。
- [ ] 确认所有既有管理功能仍可达，数据可恢复。
- [x] 更新 README 的当前实现说明；保留基线提交作为回退参照。

完成标准：阶段 A–D 的必要业务闭环均有证据；未完成项明确标为后续，不通过隐藏失败入口宣称完成。

## 6. 验收矩阵

| 编号 | 场景 | 必须验证的结果 |
|---|---|---|
| NAV-01 | 列表 → 匹配 → 目标 → 返回 | 来源与目标不混淆；选中和滚动恢复；调用次数不增加 |
| NAV-02 | 进入管理页修改后返回 | 返回原对象；读取最新资料；旧匹配失效 |
| NAV-03 | 重启应用 | 恢复有效阅读位置；不自动发起匹配或写入 |
| LIST-01 | 同 ID 三条动态 | 一张当前卡片，历史仍完整 |
| LIST-02 | 两个同名人员档案 | 两张卡，不自动合并 |
| LIST-03 | 已读、复制、新版本到达 | 已读 / 复制不改变业务排序；新版本可提示更新 |
| OWN-01 | true / false / null × 普通 / 自社限定 | 符合产品规则；空值不被写成 false |
| OWN-02 | 保存中切人、失败、重复点击 | 结果绑定原对象；失败原值；不重复写 |
| MATCH-01 | 快速连续点击多个相同入口 | 一轮有效任务，不排队重放 |
| MATCH-02 | 本地有结果、云端超时 / 部分返回 | 初筛保留；覆盖范围准确；可重试 |
| MATCH-03 | 来源或目标版本改变 | 旧结论不可继续作为当前评估使用 |
| MATCH-04 | 旧请求迟到或用户取消 | 不覆盖当前对象，不显示虚假完成 |
| BODY-01 | 超过 4,000 字符及各种换行 | 末尾条件可见，段落保留，HTML 文本不执行 |
| INTRO-01 | 从两个方向进入同一组合 | 使用正确双方资料，不重复选择 |
| INTRO-02 | 修改草稿、切模板 / 语言、返回 | 已编辑内容保留，不被自动生成覆盖 |

## 7. 验证执行方式

按改动范围选择检查，避免每次小改动重复运行全部慢测试：

- Renderer：相关组件测试；涉及壳、路由、状态恢复时运行 `App.test.tsx`。
- Main / Shared：匹配器、IPC、规则与契约测试；请求计数和部分结果必须有断言。
- 数据：改动持久化时运行 `npm run test:persistence`，业务投影运行 `npm run test:business-workbench`；涉及迁移、恢复时补充对应升级与恢复检查。
- 常规：`npm run typecheck`、`npm run test:ui-localization`、`npm run test:docs-status`、`git diff --check`。
- 阶段 B / C 的实际 Electron 验收记录交互、调用次数与结果状态；云端不可用的测试使用受控失败，不能以模拟结果冒充真实调用成功。
- 阶段 E 汇总全量测试；构建或安装包验收仅在实际执行后记录，不继承历史成功结论。

自动化测试使用虚构资料或已有隔离夹具；操作真实应用时不为验证而猜测、改写真实人员所属，不实际发送微信或邮件。

## 8. 实施风险与处理

| 风险 | 处理 |
|---|---|
| 路由与业务状态集中在 App，改壳误触发云端请求 | 先独立导航状态与明确动作，再迁移组件 |
| 聚合动态时误把同名对象合并 | 第一轮仅按稳定 ID 聚合，保留来源 |
| 双向 UI 统一时把两种召回实现硬合并 | 共用展示契约，召回保留适配器；分别验证质量 |
| 列表更新使焦点丢失或排序跳动 | 分离读状态与排序，显式更新列表 |
| 介绍使用过期匹配证据 | 绑定双方版本，变更后失效并提示刷新 |
| 新跟进与既有提案数据重复 | 阶段 D 先明确复用关系，不先建另一套 CRM |
| 布局变更掩盖已有功能 | 传统入口可达性列入阶段验收 |
