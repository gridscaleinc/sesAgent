# AI 工作规则、案件简历评估与面试问题

本次实现提供 HR 明确教规则、直接评估简历、按案件生成面试题和记录判断的完整入口。后台自动提炼、独立比较和应用核实方法已由[系统经验](./system-experience.md)实现；自动经验不修改 HR 明确设置的规则。

## HR 使用流程

- 设置 → AI 工作规则：自然语言描述经验，选择通用、指定案件或案件关键词范围，点击 AI 整理规则，查看系统理解后保存。支持修改、停用、启用和恢复历史版本。客户范围目前按案件资料中的客户关键词匹配。
- 案件列表：直接将简历拖到目标案件卡片，右侧立即打开独立的人员匹配评估面板；保留列表筛选和滚动位置。文件不会落入聊天附件流程。卡片统一提供“找人 / 查看人员”入口，点击后仍保留案件列表，右侧展示相同的人员列表。尚未建立案件版本的导入记录通过现有安全准备流程自动建立版本，不增加人工确认步骤。
- 右侧案件找人：批量查找、拖入简历、指定已有人员共用一组可展开的人员卡片，不再切换左侧匹配页。顶部固定案件及查找、添加简历入口；案件要求按需展开。查找结果可逐步展示、停止或重试，切换案件互不覆盖。批量结果也保存为同一格式的评估记录，支持反馈和历史恢复；同一案件同一人员合并，手动指定的不匹配人员不会被批量筛选隐藏。查看原简历可返回人员面板，面试安排完成可返回本案人员结果。
- 右侧评估：展示目标案件、人员、处理进度、结论、关键不满足项、逐项证据及相关项目。多份简历排队处理、切换查看；单份失败不阻断其他文件。关闭或切换面板不取消任务，迟到结果仍归属于原案件。完成记录保存在加密库，重新打开可读取该案件最近评估的最多 100 位人员；相同人员只展示最新一次结果。解析成功后评估失败只重试评估，原简历可直接打开，结果可用于介绍和业务跟进。正在处理和失败待重试的任务仅保留在当前应用会话中。
- 原有案件详情入口：拖入 PDF、DOCX 或 Excel 简历，一次最多 10 份，每份 30 MB。资料在本地解析，同内容简历复用已有记录，然后直接评估此人和当前案件。也可选已有人员评估。资料不足和条件冲突会展示依据及待确认事项。
- 评估卡：查看使用的规则和版本、记录是否推进及具体原因、重新评估，或与不加 HR 规则的评估对照。对照结果不覆盖正式评估历史；两次模型输出有自然波动。
- 面试跟进 → 本轮面试问题：结合当前案件、简历项目、有效规则和此前轮次的待确认事项生成问题。问题附要求、简历依据和评价要点，可选择后保存到本轮。案件评估卡也可以生成和复制问题。

## 规则生效方式

自然语言通过已有脱敏和 Cloud 调用通道解析为必需、优先、待确认、面试、呈现五种有限类型。Main 保存模型解析后的预览，仅接受此窗口持有的有效预览 token；界面不能直接提交任意规则结构。预览有效期 30 分钟。

规则按范围和明确的条件关键词选择，案件规则绑定稳定的 reviewId，案件修改产生新版本后继续适用。条件关键词为 AND；Java 不会误命中 JavaScript。无法准确表达的条件列为问题，不自动扩大作用范围。

必需条件逐条追加到案件要求，优先条件影响排序，待确认规则作为沟通事项，不降低已满足技术和语言要求的结论；案件原有要求不会被新规则移除。规则同时进入案件找人、人员找案件的本地评估、模型上下文和返回结果校验。批量搜索保留现有的有限候选 AI 评估机制，并非对整个资料库逐人全量调用模型；案件内指定人员评估不受候选排行截断影响。

三个入口使用相同的 `technical-language-v3` 判定：必需技术和工作语言决定能否提案；技术、语言均符合即为“可以提案”。完整简历未体现必需技术时，说明本案技术差距，不重复追问；核心资料确实为空或语言无法解释时，列出具体待补充信息。单价、出勤、地点、入场时间、商流等单独作为沟通事项，明确冲突保留原文并标为需协商，不排除专业匹配者。优先技能只影响排序。

语言核对读取专门字段、摘要及项目中的语言描述，优先解释会话等级及其原始定义。未定义的 A/B/C 不自行换算为 JLPT；工作流利描述与明确要求的证书分开核对。已知语言差距直接说明，不能写成“没有依据”。上方只列符合依据，技术或语言差距单独说明，下方列核心未知；只有结论为“可以提案”时才展示商务沟通事项，不符合或核心信息待补充时隐藏商务沟通区；按要求去重，不把模型的自由文本确认清单重新拼回结果。介绍和面试安排携带同一份沟通事项。

读取案件最近结果时，旧判定版本自动用当前资料做本地重算并新增评估记录，原历史及反馈不覆盖；页面明确区分本地重算、AI 服务不可用、云端请求失败、未返回有效评估和云端评估已完成；不会用同一句“AI 评估尚未完成”混淆这些情况。无法重算的旧结果停用旧结论，保留重新评估入口。

所有判断保留证据；不满足本案不等于给人员添加永久的能力负面标签。缺失技能不伪造证据，不自动成为学习中的技术否定事实。用户规则不能改变固定的隐私、事实依据和输出协议。规则解析校验原文引用、数值来源和必需措辞，存在语义歧义的解释仍需 HR 在预览里核对。

## 数据与一致性

案件面试出题使用统一的五维方法：履历真实性与深度（Experience）、端到端交付能力（Delivery）、问题解决能力（Troubleshooting）、独立推进与协作能力（Ownership）、项目适应与快速上手能力（Ramp-up）。每个维度固定一句母题：你过去真正做过什么、你能不能完整做完一个功能、出问题时你怎么查、你怎么独立推进并和别人协作、换到这个项目你多久能开始产出；生成时只往母题里填项目名、技术栈、职责证据和案件特有要求，简历撑不住的节拍直接去掉而不是编造。独立协作题最多三个节拍：负责范围、需与成员或负责人确认的事项、信息不明确或意见不一致时如何处理并完成交付。案件适应题的追问固定为「入场第一周就要负责小规模追加开发或障害修正时，优先确认哪些内容、如何判断自己可以开始改代码」，评价要点列出着手条件：设计书、现有实现、相关 SQL、日志、调用链、测试数据、影响范围、接口规格、既存测试。生成分两步且体现在模型输出里：第一步能力归类（capabilities），把案件要求和简历事实按五个维度分组，相关语言、框架、数据库合并为一项能力，为每个维度选定一个考察焦点和对应的简历依据；第二步从归类结果出题，每个维度最多一题，原则上 4～5 题，有案件时必须有一题案件适配，资料不足或已有明确回答时允许更少。题干必须点名简历里的具体项目或系统，让候选人自选功能只允许在点名的项目之内；每道题声明一种问法（ask），问法由各维度独占：真实性只问本人范围（系统、团队规模、模块、独立产出的设计书/代码/测试资料）或某个实际做过的技术判断，完整交付只问一个功能从需求到结合测试的端到端做法或交付物与质量确认（端到端走查只属于这一维），问题定位只问用日志、SQL、复现条件逐步缩小范围的故障链或变更应对，独立协作只问自行判断与协调汇报或不明确事项的推进，案件适配只问经验对应、入场前 1～3 天的确认顺序与最先能接的任务、或简历确实存在的差距如何补足。每种问法只属于一个维度，不同维度不可能长成同一种题。每题只问真实案例而非一般做法，一题只问一件事，完整回答应包含的要素写进评价要点并附一条注意信号，可再带一句追问（followUp），例如设计书与现行代码不一致时怎么处理。按角色选择实际问题，不能把开发、PMO、测试、运维全部套成障害改修题。技术名词和字段不是逐项出题单位。

生成输入排除单价、入场时间、地点、出勤等营业字段，案件标题中的【】标签（测试编号、急募、地区等）不作为要求；无效、含义不明、占位数据不用于出题。输出校验：最多五题、归类维度唯一、每题的维度和来源引用必须落在归类结果之内、问法必须属于该题维度、文本去重、营业条件、让候选人自选时题干必须含所引用的简历项目名、不得问一般做法、有案件时必须有一题案件适配、最多一题没有简历依据。校验不通过时带具体原因自动重试一次，再失败才提示重新生成；云端调用本身的失败不重试。题库模板为可选参考，自动学习方法也不能覆盖这些约束。没有指定案件的招聘面试只基于简历，不虚构当前案件适配题。历史题单保持不变，新生成的问题使用新规则。

案件评估卡生成的面试题按人员×案件保存为草案（`case_person_question_drafts`，schema 58），带简历、案件、规则三个版本号和 experienceRunId；同一对人员案件只保留一份有效草案，旧草案标记为已替代。从评估卡或提案文进入「安排面试」后，跟进页在未排期时提示草案存在；排期建立第一轮时，store 直接把版本一致的草案写入 questionPlan（事件记为「带入评估时生成的 N 道面试题」），跟进页和人员侧的面试准备页读到的是同一份持久化题单；HR 调整后仍通过 prepare 保存，经验学习据此看到相对草案的改动。改动前已建立的空轮次打开「本轮面试问题」时仍会带入草案供保存。三个版本号任一变化即视为过期：评估卡和跟进页只提示重新生成，不带入。生成面试题不创建跟进记录，题目也不进入提案文。

出题来源使用请求内的要求编号与简历证据编号。模型可组合多个编号验证关联能力；Main 校验编号属于本次输入且不重复，再从实际资料回填脱敏后的要求和证据。模型不再输出需要逐字比对的来源文本，避免合并技能或调整措辞造成误拦；不存在的编号、把要求当作简历证据、额外生成的证据字段仍会被拒绝。

Schema 52 新增规则版本、人员案件评估、评估反馈三张表，保存在现有加密数据库。规则修改、停用及恢复均产生新版本；并发旧版本写入被拒绝。评估绑定人员版本、案件版本及规则库版本，旧结果标记历史状态。面试题保存时再次核验对应资料和规则版本。

反馈附带评估 ID、是否推进、原因和补充说明。档期、单价、本人意向、案件关闭等分别记录，为后续学习提供区分业务原因的样本；当前不将一次未推进自动转换成技能负样本。

## 验证

- `npm test`：包含规则原文校验、作用范围、双向匹配、IPC 预览隔离、界面导入及问题证据校验。
- `npm run test:work-rules`：Electron 原生加密 SQLite 验证版本恢复、过期写入、评估和反馈存储、面试题保存及重启读取。
- `npm run test:schema-upgrade`、`npm run test:schema-v37-agent`：旧数据库升级。
- `npm run test:business-progress`、`npm run test:persistence`：现有流程及持久化回归。
- `npm run typecheck`、`npm run test:ui-localization`、`npm run test:docs-status`。

真实模型输出质量需要在已连接的 AI 服务上使用实际案件和授权简历验收。发布构建仍要求项目原有的产品 Gmail OAuth 配置；开发验证不等于已生成可分发安装包。

案件内明确指定简历时，可以复用已归档记录的当前资料进行单人评估和出题；归档状态保持不变，批量找人、后台机会发现仍排除归档人员。重复文件继续复用原记录和资料版本，界面说明归档复用；失效版本和已删除资料仍不可评估。`npm run test:case-resume-assessment` 使用合成 Excel、真实解析进程、加密数据库、桌面 IPC 与真实 Electron 渲染窗口验证新导入、归档重复导入、进度事件、案件历史、列表拖入、统一查找、跨入口去重、批量结果反馈保存、关闭后重开、重试和出题，模型返回为测试替身。界面截图及报告位于忽略目录 `output/case-resume-ui/`。
